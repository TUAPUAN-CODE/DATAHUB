# ข้อมูล 1 ล้านแถวต่อตาราง — ช้าไหม และแก้อย่างไร

> สรุปตรงๆ: **บางการทำงานจะช้ามาก** ถ้าไม่ปรับ — โดยเฉพาะ ค้นหาข้อความ, เรียงตามคอลัมน์ข้อความ, กรอง "มีคำว่า…", และรายการค่าในตัวกรอง
> ตัวเลขเวลาจริงต้องวัดบนฐานข้อมูลของคุณ (ผมทดสอบกับ SQL Server จริงที่นี่ไม่ได้) จึงทำเครื่องมือวัดให้: `npm run bench`

## ทำไมถึงช้า (โครงสร้างข้อมูล)
ข้อมูลเก็บแบบ 1 เซลล์ = 1 แถวในตาราง `Cells` (EAV) ตารางที่มี 1,000,000 แถว × 12 คอลัมน์ = **~12 ล้านแถวใน Cells**

| การทำงาน | ผลที่ 1 ล้านแถว | เหตุผล |
|---|---|---|
| เปิดหน้าแรก ไม่เรียง ไม่กรอง | **เร็ว** | ใช้ดัชนี `Rows(sheet, is_deleted, row_order)` อ่านเฉพาะหน้า |
| นับจำนวนแถวทั้งหมด (ทุกครั้งที่เปลี่ยนหน้า) | ปานกลาง | อ่านดัชนีทั้งช่วง → **ทำ cache แล้ว** (เกิน 50,000 แถว จำ 20 วินาที) |
| เรียงตามคอลัมน์ตัวเลข/วันที่ | ช้า (วินาที) | ต้องดึงค่าของทุกแถวมาเรียง → ดัชนีใน `optional/13_scale_indexes.sql` ช่วย |
| เรียงตามคอลัมน์ **ข้อความ** | **ช้ามาก** | `value_text` เป็น NVARCHAR(MAX) ทำดัชนีไม่ได้ ต้องอ่านทั้งตาราง Cells |
| กรอง "เท่ากับ/มีคำว่า" ข้อความ | **ช้ามาก** | เหตุผลเดียวกัน |
| **ค้นหาในชีต (ทุกคอลัมน์)** | **ช้าที่สุด** | `LIKE '%…%'` อ่านทุกเซลล์ 12 ล้านเซลล์ — **ระบบปฏิเสธแล้ว** เมื่อชีตเกิน 300,000 แถวและยังไม่ได้กรองคอลัมน์ใดก่อน (ตั้งค่าได้ด้วย `BIG_SHEET_ROWS`) |
| รายการค่าในตัวกรอง (ติ๊กเลือก) | ช้า | `GROUP BY` ทั้งคอลัมน์ |
| ย้ายไปหน้าลึกๆ (หน้า 5,000) | ช้า | `OFFSET` ต้องข้ามแถวก่อนหน้า |
| ประวัติการแก้ไข `CellHistory` | โตไม่หยุด | 1 แถวต่อการแก้ 1 เซลล์ → ต้องมีนโยบายเก็บ/ย้ายข้อมูลเก่า |

## ทำอะไรไปแล้ว
1. **cache จำนวนแถว** ของชีตใหญ่ + ล้างทันทีเมื่อมีการเพิ่ม/ลบแถว (`services/rowCount.ts`)
2. **กันการค้นหาข้อความทั้งชีต** บนชีตใหญ่ที่ยังไม่ได้กรอง — ป้องกันคำสั่งเดียวทำให้ฐานข้อมูลหนักจนทุกคนช้า (ข้อความบอกให้กรองด้วยวันที่ก่อน)
3. **เครื่องมือวัด** `npm run bench -- --sheet <id> --seed 1000000` (ใช้ **ชีตทดสอบ** บนฐานข้อมูลสำเนา) พิมพ์ตารางเวลามัธยฐานของคำสั่งหลักๆ
4. **สคริปต์ดัชนีเสริม** `database/optional/13_scale_indexes.sql` (ไม่รันอัตโนมัติ — DBA รันช่วง maintenance แล้ววัดซ้ำ)
5. จำการกรอง/เรียงของแต่ละ account (ข้อ 13) → เปิดชีตมาเจอมุมมองที่กรองวันที่ไว้แล้ว ไม่ต้องเปิดทั้ง 1 ล้านแถว

## ลำดับที่แนะนำ (ทำตามนี้ ได้ผลมากที่สุดก่อน)
1. **แยกตารางตามช่วงเวลา** (คุณทำอยู่แล้ว: ไฟล์ปี → ชีต/ไฟล์เดือน เช่น October, November) — ตารางละ ≤ ~200,000 แถว ทุกอย่างเร็วโดยไม่ต้องแก้โครงสร้าง; ดูข้ามเดือนใช้ Union sheet
   และ**ย้ายข้อมูลเก่า**ไปไฟล์ปี/archive เมื่อพ้นช่วงใช้งาน (เช่น เกิน 12 เดือน)
2. **วัดจริง**: สร้างชีตทดสอบ + `npm run bench` บนฐานข้อมูลสำเนา ก่อน/หลังรัน `optional/13_scale_indexes.sql` — ถ้า "เรียง/กรองตัวเลขและวันที่" เหลือน้อยกว่า ~1.5 วินาทีที่ 1 ล้านแถว ก็พอ
3. **ถ้ายังต้องเรียง/กรองข้อความบนตารางล้านแถว**: เพิ่มคอลัมน์คำนวณ persisted `LEFT(value_text, 200)` + ดัชนี แล้วให้ตัวสร้างคำสั่งใช้คอลัมน์นั้น (ผมทำให้ได้หลังเห็นผล bench — ไม่แนะนำให้ทำก่อนวัด เพราะ ALTER บนตาราง 12 ล้านแถวใช้เวลาและพื้นที่ log มาก)
4. **การค้นหาข้อความทั้งชีต**: เปิด SQL Server Full-Text Search บน `Cells.value_text` แล้วใช้ `CONTAINS` (คำเต็ม/ขึ้นต้นคำ) แทน `LIKE '%…%'`
5. **รายงาน/แดชบอร์ดบนข้อมูลล้านแถว**: อ่านจาก **replica ที่อ่านได้อย่างเดียว** (Always On Secondary — ดู `docs/HA.md`) เพื่อไม่ให้รายงานหนักไปแย่งกับคนบันทึกข้อมูลหน้างาน
6. **ประวัติการแก้ไข**: กำหนดนโยบาย เช่น เก็บ 13 เดือน แล้ว archive/ลบเป็นชุดนอกเวลางาน
7. **Keyset paging** (เลื่อนหน้าด้วย "ค่าล่าสุดที่เห็น" แทน OFFSET) สำหรับหน้าลึกๆ — ทำได้เมื่อมีดัชนีเรียงตามคอลัมน์ที่ต้องการ

## ฝั่งเบราว์เซอร์/มือถือ
เบราว์เซอร์ไม่เคยถือทั้ง 1 ล้านแถว — โหลดทีละหน้า (50–1000 แถว) เท่านั้น มือถือเริ่มต้นที่ 50 แถว/หน้า
