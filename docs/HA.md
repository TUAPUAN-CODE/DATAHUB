# ใช้งาน 2 server + ฐานข้อมูลสำรอง (Load balancer + Always On)

```
   ผู้ใช้ (PC / มือถือ)
          │
   ┌──────▼───────┐        ← ตัวกระจายคำขอ (nginx / HAProxy)  *ต้องมีสำรองเอง ดูหัวข้อ "จุดที่ยังเป็นจุดเดียว"
   │ Load balancer│
   └───┬──────┬───┘
       │      │
 ┌─────▼──┐ ┌─▼──────┐        DataSheet Pro server ×2  (.116 และ .115)  — โค้ดชุดเดียวกัน, .env เกือบเหมือนกัน
 │  .116  │ │  .115  │◄─────► Redis (ให้สองเครื่อง "ได้ยินกัน": อัปเดตสด + ล้าง cache)
 └───┬────┘ └───┬────┘
     │          │         โฟลเดอร์แชร์ (รูป / คลังเอกสาร) ที่ทั้งสองเครื่องเห็นเหมือนกัน
     └────┬─────┘
   ┌──────▼──────────┐
   │ AG Listener     │   ← ชื่อเดียวที่แอปต่อ (DB_HOST) ตามไปหาเครื่อง SQL ที่เป็น Primary เอง
   │ SQL-A  ⇄  SQL-B │   ← Always On: ข้อมูลสองเครื่องเหมือนกัน
   └─────────────────┘
```

## 1) สองเครื่องแอป + Load balancer

**ที่โค้ดจัดการให้แล้ว** (repo นี้):
- **งานที่ต้องรันเครื่องเดียว** (แจ้งเตือน LINE, ตัวเชื่อมเครื่องอ่าน RFID — เครื่องอ่านรับการเชื่อมต่อได้ 1 ตัว —, ล้างถังขยะ): เครื่องไหนถือ "lease" (ตาราง `ServiceLeases` ใน SQL) เป็นคนรัน; ถ้าเครื่องนั้นดับ อีกเครื่องรับช่วงเองภายใน ~30 วินาที — ไม่ต้องตั้งค่าว่าเครื่องไหนเป็นหลัก
- **อัปเดตสด (Socket.IO) ข้ามเครื่อง**: คนที่ต่อ .116 เห็นสิ่งที่คนที่ต่อ .115 แก้ทันที ผ่าน Redis (ตั้ง `REDIS_URL`)
- **cache ที่ต้องล้างพร้อมกัน** (สิทธิ์โฟลเดอร์, ข้อมูลผู้ใช้/สิทธิ์, จำนวนแถว): ส่งข้อความล้างผ่าน Redis — เปลี่ยนสิทธิ์บนเครื่องหนึ่งมีผลอีกเครื่องทันที
- **migration ตอนเริ่มระบบ**: ล็อกด้วย app lock — เปิดสองเครื่องพร้อมกันไม่ชนกัน
- `/api/health` บอกว่าเครื่องไหนตอบ (`node`) และเครื่องนี้รันงานเดี่ยวอะไรอยู่ (`runs`) — ใช้ตรวจ และให้ LB เช็คสุขภาพ

**ที่ต้องตั้งค่า** (ทั้งสองเครื่อง):
1. `server/.env` — `JWT_SECRET` **ค่าเดียวกัน**, `DB_*` ชี้ฐานเดียวกัน, `NODE_ID` ไม่ซ้ำกัน (เช่น `app116`, `app115`), `REDIS_URL`, `PUBLIC_URL`/`CORS_ORIGIN` = ที่อยู่ของ Load balancer
2. `UPLOAD_DIR` และ `ARCHIVE_DIR` ชี้ **โฟลเดอร์แชร์เดียวกัน** (เช่น `\\fileserver\dochub\uploads`) — ไม่งั้นรูปที่อัปโหลดผ่านเครื่อง A จะไม่เห็นบนเครื่อง B
3. `GATEWAY_ENABLED=1` ใส่ได้ทั้งสองเครื่อง (lease เลือกให้ต่อเครื่องอ่านจริงแค่เครื่องเดียว); `LINE_CHANNEL_*` ใส่ทั้งสอง
4. build client เวอร์ชันเดียวกัน (`SERVE_CLIENT_DIR`) หรือให้ nginx เสิร์ฟไฟล์ static
5. Redis: ติดตั้งบนเครื่องใดเครื่องหนึ่งหรือเครื่องแยก (`redis://host:6379`) — ถ้า Redis ล่ม เว็บยังใช้ได้ แต่สองเครื่องจะหยุด "ได้ยินกัน" ชั่วคราว (อัปเดตสดข้ามเครื่องหาย, cache สิทธิ์ล้างช้าสุด 30 วินาที)

**Load balancer**: ไฟล์ตัวอย่าง `deploy/nginx.conf` (ทุกระบบ) หรือ `deploy/haproxy.cfg` (Linux; เช็คสุขภาพ `/api/health` ทุก 2 วินาทีและเอาเครื่องที่เสียออกเอง)
- nginx แบบฟรีเช็คสุขภาพแบบ "ลองแล้วพัง": เครื่องที่ตอบ error 2 ครั้งติดจะถูกพัก 10 วินาที แล้วคำขอ GET ถูกส่งไปอีกเครื่องเอง; **POST ไม่ถูกส่งซ้ำ** (กันบันทึกซ้ำสองครั้ง) จึงอาจมีผู้ใช้ 1–2 คนที่กดบันทึกพอดีตอนเครื่องดับแล้วต้องกดซ้ำ
- ใช้ `ip_hash` (คนเดิมเข้าเครื่องเดิม) เพราะสำรอง polling ของ Socket.IO ต้องการ; WebSocket ปกติไม่ต้อง

**ทดสอบ (ทำตามนี้ก่อนใช้จริง)**
1. เปิดสองเครื่อง + LB, เปิด `http://<LB>/api/health` รีเฟรชหลายครั้ง ต้องเห็น `node` สลับกัน
2. เปิดชีตเดียวกันสองเบราว์เซอร์ (ให้ได้คนละเครื่อง — ดู `node` จาก header/ทดสอบด้วยปิดเครื่องใดเครื่องหนึ่ง) แก้เซลล์ → อีกฝั่งเห็นทันที
3. ปิด process ของเครื่องหนึ่ง → ภายใน ~10–30 วินาที ใช้งานผ่าน LB ต่อได้ และ `/api/health` ของอีกเครื่องแสดง `runs` มีงานเดี่ยวครบ (`line-alerts`, `rfid-gateway`, `trash-purge`)
4. เปิดเครื่องที่ปิดกลับ → ไม่เกิดการต่อเครื่องอ่าน RFID ซ้ำ (เครื่องอ่านต้องไม่หลุด)

## 2) ฐานข้อมูล Always On (2 เครื่อง)

โค้ดฝั่งแอปทำให้แล้ว (ไม่ต้องแก้โค้ดอีก): ต่อผ่านชื่อ **AG Listener** (`DB_HOST=<listener>`, `DB_MULTI_SUBNET_FAILOVER=true`), ถ้าเชื่อมต่อหลุดตอน failover จะสร้าง connection ใหม่เองและลองคำสั่ง **อ่าน** ซ้ำสูงสุด 3 ครั้ง (คำสั่ง **เขียน** ลองซ้ำเฉพาะกรณีที่แน่ใจว่ายังไม่ได้ทำงาน) — ผู้ใช้จะเห็นช้าไปไม่กี่วินาทีตอน failover ไม่ใช่ error

การติดตั้ง Always On เป็นงานของ DBA/ผู้ดูแล Windows Server (ผมทำให้จากที่นี่ไม่ได้) โครงร่างอยู่ใน `deploy/always-on-skeleton.sql` สิ่งที่ต้องรู้ก่อนเริ่ม:

| หัวข้อ | รายละเอียด |
|---|---|
| ข้อกำหนด | เครื่อง SQL ทั้งสองอยู่ใน **Windows Server Failover Cluster (WSFC)** เดียวกัน, SQL Server รุ่นเดียวกัน, ฐานข้อมูลต้องเป็น **FULL recovery** |
| รุ่น SQL Server | **Standard** ทำ *Basic Availability Group* ได้ (2 เครื่อง, **1 ฐานข้อมูลต่อ AG**, secondary อ่านไม่ได้) — พอสำหรับฐาน `DataSheetPro` ฐานเดียว; **Enterprise** ได้ secondary ที่อ่านได้ (ใช้รัน รายงานหนักๆ ได้) |
| 2 เครื่อง = ต้องมี **Witness** | ถ้ามีแค่ 2 โหนด ต้องมี File Share Witness (หรือ Cloud Witness) ไม่งั้น cluster ตัดสินใจ failover อัตโนมัติไม่ได้เมื่อเครื่องหนึ่งดับ |
| ข้อมูลเหมือนกันทั้งสอง | ใช้ `SYNCHRONOUS_COMMIT` + `FAILOVER_MODE = AUTOMATIC` — เขียนลงครบทั้งสองเครื่องก่อนตอบผู้ใช้ (ช้ากว่าเล็กน้อย แต่ข้อมูลไม่หาย) |
| Listener | ชื่อ/IP เดียวที่แอปต่อ ตามไปหาเครื่อง Primary เอง |
| สิ่งที่ **ไม่** ถูกคัดลอก | SQL **Login** (ต้องสร้างบนอีกเครื่องด้วย **SID เดียวกัน**), SQL Agent jobs, linked server — ถ้าลืม Login หลัง failover แอปจะ login ไม่ได้ |
| การสำรองข้อมูล | Always On **ไม่ใช่ backup** (ลบผิดก็ลบทั้งสองเครื่อง) ยังต้อง backup เป็นประจำ |
| ทดสอบ | ทดสอบ failover ด้วยมือตอนไม่มีคนใช้ (SSMS: Failover wizard) แล้วเปิดเว็บ — ต้องใช้งานต่อได้ภายในไม่กี่วินาที |

## จุดที่ยังเป็นจุดเดียว (ต้องวางแผนต่อ)
- **Load balancer เอง** — ถ้า nginx เครื่องเดียวดับ ผู้ใช้เข้าไม่ได้ทั้งที่แอป 2 เครื่องปกติ ทางแก้: nginx/HAProxy 2 ตัว + IP เสมือน (keepalived บน Linux, หรือ Windows NLB/ฮาร์ดแวร์ LB ขององค์กร)
- **Redis** (ถ้าล่ม เว็บยังใช้ได้ แต่ฟีเจอร์ข้ามเครื่องช้า/หาย) — ใช้ Redis Sentinel หากต้องการสำรอง
- **โฟลเดอร์แชร์ของรูป** — ต้องสำรอง/ทำ HA ที่ชั้นของไฟล์เซิร์ฟเวอร์
- **ตัวเครื่องอ่าน RFID และ Print Agent** — อุปกรณ์เดียวต่อเครื่องอ่านตามธรรมชาติ
