## 0. แกนกลางที่ทุกข้อใช้ร่วมกัน (ควรทำก่อน)

ข้อ 2–6 ดูเหมือนแยกกัน แต่ใช้ฐานเดียว 3 ชิ้น — ทำชิ้นเหล่านี้ให้ดีแล้วแต่ละฟีเจอร์เป็นแค่ "ตั้งค่า" ไม่ใช่โค้ดใหม่ทั้งก้อน:

| ฐาน | คืออะไร | ใช้กับข้อ |
|---|---|---|
| **Row Links** | ตาราง `RowLinks(parent_row, child_row, qty, unit, role, created_at)` — ความสัมพันธ์ "แถวนี้มาจาก/อยู่ใน แถวนั้น" | 4 ผสม, 5 รถเข็น, 6 traceback |
| **Entry Rule** | กติกาต่อคอลัมน์: ใครกรอกได้ (พิมพ์/สแกน/อุปกรณ์) และต้องตรวจกับตารางไหนก่อนรับค่า (บังคับที่ server ผ่าน `registerColumnGuard` ที่มีอยู่แล้ว) | 2, 3 |
| **Device Event** | เหตุการณ์จากอุปกรณ์ที่ทำให้เป็นรูปแบบเดียวกัน `{deviceId, kind, value, ts}` เข้าคิวเดียว | 2, 3 |

หลักการเดิมที่ยังใช้: แต่ละโมดูลเป็นอิสระ (ลงทะเบียนผ่าน hooks, ไม่แก้แกนกลาง), ไม่ผูกกับชื่อคอลัมน์ตายตัว, ทำงาน **ฝั่ง server** เสมอ (บทเรียนจากสลีป: ถ้าพึ่งหน้าเว็บที่เปิดอยู่ ปิดหน้าแล้วงานหยุด)

## 2. รับข้อมูลจาก RFID / IoT

### คำตอบสั้น: ทำทั้งสองแบบ แต่แยกบทบาท
- **เมนูซ้าย "อุปกรณ์"** = ที่ *จัดการอุปกรณ์* (เพิ่ม/แก้/เปิด-ปิดเครื่องอ่าน, ดูสถานะ, ดูข้อมูลสด, ผูก EPC ที่ไม่รู้จัก) หน้าตาคล้าย `RFIDCSCheckOutPage`
- **ในตาราง** = ที่ *ใช้งาน* มีปุ่ม "รับจากอุปกรณ์: เปิด/ปิด" บนแถบเครื่องมือของชีต (ปิด-เปิดเฉพาะชีตนี้ ไม่ใช่ปิดเครื่องอ่านทั้งโรงงาน)

เหตุผล: เครื่องอ่าน 1 เครื่องอาจป้อนหลายตาราง และคนหน้างานต้องการสวิตช์ง่ายๆ ในตารางที่ตัวเองทำงาน ส่วนผู้ดูแลต้องการหน้ารวมเห็นสุขภาพของอุปกรณ์ทุกตัว

### สถาปัตยกรรม
```
[RFID reader TCP] [บาร์โค้ดเครื่องอ่าน serial] [MQTT เซนเซอร์] [HTTP/webhook] [ตาชั่ง]
        \                |                         |              |            /
         └──────── Device Gateway (process แยก, fork เดียว, มี driver ต่อชนิด) ────────┘
                         │  ทำให้เป็น Device Event เดียวกัน + กรองซ้ำ/ขยะ
                         ▼
              POST /api/devices/events  (device key / HMAC, ไม่ใช้ login ผู้ใช้)
                         ▼
        Rule Engine (server) ── ตาม DeviceBindings ──► เขียนเซลล์/สร้างแถว (ผ่าน cellWriter เดิม → history, formula, alert ทำงานต่อเอง)
                         ▼
                 Socket.IO → หน้าเว็บอัปเดตสด
```
- **Gateway แยก process** เหมือน `RFIDc1.js` (ต้อง fork เดียว ห้าม cluster เพราะเครื่องอ่านรับ connection เดียว) — driver เป็นปลั๊กอิน เพิ่มชนิดอุปกรณ์ใหม่โดยไม่แตะระบบหลัก
- นำบทเรียน hardening เดิมมาเป็นมาตรฐานของ gateway: frame buffer, watchdog/reconnect, กรอง EPC ขยะ, debounce ต่อ (device, value), TLS/คีย์จาก env

### ตาราง (ใหม่)
| ตาราง | เก็บ |
|---|---|
| `Devices` | device_id, ชื่อ, kind (rfid/barcode/mqtt/http/scale), config(JSON), key_hash, enabled, last_seen, status |
| `DeviceEvents` | log ดิบ (value, ts, device, ผลการประมวลผล: ok/ignored/unknown/error) เก็บ N วัน — ใช้ debug และ traceback |
| `DeviceBindings` | อุปกรณ์ ↔ ชีต: enabled, โหมด (ดูด้านล่าง), คอลัมน์ปลายทาง, เงื่อนไข |
| `TagRegistry` | EPC → เป็นของอะไร (รถเข็น tro_id, ภาชนะ …) แทน flow "EPC ไม่รู้จัก → ผูก tro_id" เดิม ใช้ร่วมได้ทุกชีต |

### โหมดของ Binding (เลือกต่อชีต)
1. **เติมค่าในแถวที่เลือก/แถวปัจจุบัน** (เช่น สแกนเพื่อลงเวลาเข้าห้องเย็นของแถวนี้)
2. **สร้างแถวใหม่** ต่อการสแกน (เช่น รับเข้า: แต่ละคันที่ผ่านเครื่องอ่านเป็นหนึ่งแถว)
3. **ค้นหาแถวตามค่า** (สแกนรถเข็น → หาแถวที่ tro_id ตรง แล้วทำ "การกระทำ" เช่น ตั้งเวลาออก)
4. **ทริกเกอร์การกระทำ** เช่น พิมพ์สลีป (ใช้ print-agent เดิม ทำงานฝั่ง server ไม่ต้องเปิดหน้า)

> ถ้าอุปกรณ์เป็นเซนเซอร์ต่อเนื่อง (อุณหภูมิ) → โหมด "บันทึกเป็นแถวตามเวลา" + แจ้งเตือนเมื่อเกินเกณฑ์ด้วยระบบ LINE ที่ทำแล้ว

### ความเสี่ยง/ข้อควรระวัง
- เครื่องอ่านอ่านซ้ำ 1 ป้ายหลายครั้ง → ต้อง debounce + คีย์กันซ้ำ (device, value, หน้าต่างเวลา)
- ต้องมี "โหมดจำลอง" (ส่ง event ปลอมเข้า endpoint เดียวกัน) เพื่อทดสอบโดยไม่ต้องมีเครื่องอ่านจริง
- สิทธิ์: ผู้ใช้เปิด/ปิดอุปกรณ์ได้เฉพาะชีตที่ตัวเองมีสิทธิ์จัดการ; จัดการอุปกรณ์ (เพิ่ม/ลบ) เป็นแอดมิน

## 3. คอลัมน์แบบ "Scanner" ที่ตรวจกับตารางอื่นก่อนรับค่า

### การตั้งค่าในคอลัมน์ (ต่อยอดจากตัวแก้ไขคอลัมน์เดิม)
```jsonc
validation.entry = {
  "mode": "scan" | "scan_or_type" | "type" | "device",
  "parse": { "split": "|", "index": 3 },          // สลีป QR "14M…|…|695089|245|kg|PFCM" → เอาช่องที่ 4 (mapping_id)
  "verify": {
    "sheetId": "…", "keyColumnId": "…",           // ตารางอ้างอิง + คอลัมน์ที่ต้องตรงกับค่าที่สแกน
    "onMiss": "reject" | "warn" | "allow",        // ไม่พบ: ปฏิเสธ / เตือนแต่ให้ผ่าน / ให้ผ่าน
    "fill": [ { "from": "ชื่อวัตถุดิบ", "to": "<คอลัมน์ในตารางนี้>" } ]   // เติมคอลัมน์อื่นให้อัตโนมัติจากแถวที่เจอ
  },
  "unique": true                                  // ห้ามสแกนซ้ำ (เช่น รถเข็นคันเดิมเข้าซ้ำ)
}
```
- ใช้ **เอนจิน LOOKUP เดิม** (อ่านชีตอื่น, สิทธิ์ตรวจตอนตั้งค่า, ผู้ใช้ทั่วไปไม่ต้องเปิดไฟล์ต้นทางได้) — ไม่เขียนระบบค้นหาใหม่
- **บังคับที่ server** (`registerColumnGuard` / hook ก่อนเขียนเซลล์) ไม่ใช่แค่หน้าเว็บ → สแกนจากอุปกรณ์/API ก็ผ่านกติกาเดียวกัน
- แหล่งสแกน: เครื่องสแกนแบบ keyboard-wedge (พิมพ์ลง input), กล้องมือถือ, RFID (ผ่านข้อ 2)
- ประสบการณ์ใช้งาน: ช่อง "สแกนที่นี่" โฟกัสอัตโนมัติ, สแกนผ่าน → เสียง/สีเขียว + เติมค่า, ไม่ผ่าน → เสียง/สีแดง + ข้อความเหตุผล (ไม่ผ่านต้องไม่เงียบ — คนหน้างานรีบ)
- ข้อจำกัดที่ต้องตัดสินใจ: ถ้า `verify` ชี้ตารางใหญ่มาก ต้องมี index/แคชค้นหา (ตอนนี้แคช 5 วินาที, เพดาน 200,000 เซลล์ — ถ้าเกินให้ทำ lookup แบบ query ตรง)

## 4. ผสมวัตถุดิบ: แถว 1 + 2 → แถว 3

### โมเดล
วัตถุดิบ/ล็อตแต่ละแถวคือ "หน่วยหนึ่ง" มี id (doc_number auto เดิมใช้ได้) การผสมคือ **การกระทำ** ที่:
1. เลือกแถวต้นทาง 1..n (สแกนหรือเลือก) พร้อม **ปริมาณที่ใช้** จากแต่ละแถว
2. สร้างแถวใหม่ (ล็อตผสม) ในชีตปลายทาง — ปริมาณรวม = ผลรวม (หรือกรอกเองถ้ามีสูญเสีย)
3. บันทึกใน `RowLinks` (role = `mix_input`) ทุกต้นทาง → ล็อตใหม่
4. ตัดยอดคงเหลือของต้นทาง (คำนวณจาก `ปริมาณเดิม − SUM(qty ที่ถูกนำไปใช้)` ไม่ใช่เขียนทับ → ย้อนดูได้ แก้ผิดได้)

### ที่ต้องมี
- **ตรวจปริมาณ**: ใช้เกินคงเหลือไม่ได้ (ตรวจใน transaction เดียวกัน กันสองคนผสมจากล็อตเดียวพร้อมกัน)
- **ตรวจความเข้ากันได้** (ตัวเลือก): กติกา เช่น ประเภทเดียวกัน/ห้ามผสมข้ามกลุ่ม ตั้งเป็น Entry Rule ของปุ่มผสม
- **ผสมหลายชั้นได้**: ล็อต 3 ไปผสมต่อเป็นล็อต 5 ได้ → traceback เดินย้อนเป็นต้นไม้
- UI: ปุ่ม "ผสม" บนแถบเครื่องมือ → หน้าต่าง: สแกน/เพิ่มต้นทางเป็นรายการ + ปริมาณ → ดูตัวอย่างล็อตใหม่ → ยืนยัน (ทั้งหมดสำเร็จหรือล้มทั้งหมด)
- ฟังก์ชันสูตรที่จะเพิ่ม: `LINKED_SUM(คอลัมน์)`, `LINKED_COUNT()` เพื่อคำนวณคงเหลือ/จำนวนต้นทางในตารางได้โดยไม่เขียนโค้ด

### ทางเลือกที่ไม่แนะนำ
ใส่ "รหัสต้นทาง 1, 2" เป็นข้อความในช่องเดียว — ง่ายแต่ traceback/ตัดยอดไม่ได้ ค้นย้อนช้า และผิดพลาดง่าย

## 5. รถเข็น 1 คัน มีหลายวัตถุดิบ

### โมเดล: Header / Lines (หัว-รายการ) แทนการยัดหลายวัตถุดิบในแถวเดียว
- **ชีตรถเข็น (Header)**: 1 แถว = 1 คัน/1 เที่ยว (tro_id, สถานะ, เวลาเข้า-ออก, ที่เก็บ)
- **ชีตรายการ (Lines)**: 1 แถว = 1 วัตถุดิบบนรถเข็น (mapping_id, วัตถุดิบ, น้ำหนัก, ล็อต) เชื่อมกับ Header ด้วย `RowLinks` (role = `contains`) หรือคอลัมน์อ้างอิง
- UI: แถว Header กางออกเห็นรายการข้างใน (master-detail) — เหมือนหน้า CheckOut ที่เห็นหลายวัตถุดิบ/คัน

### การทำงาน
- **สแกนรถเข็น (RFID/QR) → ระบบหา Header → การกระทำใช้กับ Lines ทั้งหมดพร้อมกัน** เช่น "ออกห้องเย็น" ลงเวลาให้ทุกรายการ (การกระทำชุดเดียว, history ครบรายการ)
- ลงเวลา/สถานะได้ทั้งระดับรถเข็นและระดับรายการ (เวลา delay ของแต่ละวัตถุดิบยังแยกกัน — ใช้ระบบเวลามาตรฐานตามประเภทที่ทำแล้ว)
- **แยก/รวมรถเข็น** = ย้ายรายการจาก Header หนึ่งไป Header อื่น (บันทึกเป็นเหตุการณ์ ไม่ลบประวัติ)
- **พิมพ์สลีป**: ตัวออกแบบ PDF เดิมรองรับ "ตารางลูก" ใน 1 ใบต่อรถเข็น หรือ 1 ใบต่อวัตถุดิบ (เหมือน `materials[]` ของสลีปเดิม)
- ผูกกับข้อ 2/3: สแกนรถเข็น → `TagRegistry` หา tro_id → Header

### ข้อควรระวัง
- รถเข็นถูกใช้ซ้ำหลายเที่ยว → Header ต้องเป็น "เที่ยว" ไม่ใช่ตัวรถเข็นถาวร (ไม่งั้นประวัติปนกัน)
- ผสมบนรถเข็น (ข้อ 4) = ผลลัพธ์ล็อตใหม่ถูกวางเป็นรายการบน Header ใหม่ ต้นทางเดิมอยู่ใน Header เดิมจนกว่าจะตัดยอดหมด

## 6. Traceback (ย้อนรอย)

### สองทิศทาง
- **Backward**: ล็อต/สลีปนี้ทำมาจากอะไร (ต้นทางทุกชั้น, ซัพพลายเออร์/วันที่รับ)
- **Forward**: วัตถุดิบล็อตนี้ไปอยู่ที่ไหนบ้าง (ล็อตผสมไหน, รถเข็นไหน, ส่งออกไปที่ไหน) — ใช้ตอนเรียกคืนสินค้า

### ข้อมูลที่ใช้ (ไม่มีตารางใหม่เพิ่ม)
- `RowLinks` → โครงสร้างต้นไม้ (SQL recursive CTE ทั้งสองทิศ, จำกัดความลึก/ตัดวงวน)
- ประวัติเซลล์เดิม (`Cells` history/audit) → เวลาแต่ละขั้น + ใครลงข้อมูล
- `DeviceEvents` → หลักฐานว่าถูกสแกนที่เครื่องไหนเวลาใด
- เวลามาตรฐาน + ระดับสีที่ทำแล้ว → แสดง delay ของแต่ละขั้นด้วยสีเดียวกับในตาราง

### หน้าจอ "Traceback" (เมนูซ้าย)
1. ช่องค้นหา: สแกน/พิมพ์ ล็อต, mapping_id, tro_id, EPC → เลือกทิศทาง
2. **ต้นไม้/กราฟ** ซ้าย-ขวา (โหนด = ล็อต, ขอบ = ปริมาณที่ใช้) กดโหนดดูรายละเอียด
3. **ไทม์ไลน์** ของโหนดที่เลือก: เตรียมเสร็จ → เข้าห้องเย็น → ออก → บรรจุ พร้อมเวลาที่ใช้ vs มาตรฐาน (สี)
4. ปุ่มส่งออก PDF/Excel (ใช้ระบบ PDF designer + คลังเอกสารที่มี) — แม่แบบ "รายงานย้อนรอย" ออกแบบเองได้
5. สิทธิ์: ผู้ใช้เห็นโหนดที่ไม่มีสิทธิ์เปิดไฟล์ต้นทางเป็นข้อมูลสรุป (ชื่อล็อต/เวลา) ตามหลักเดียวกับ LOOKUP

### การย้ายข้อมูลเดิม
ล็อตเก่าจาก PFCMv2 ที่ผสมไว้แล้ว ต้องนำเข้าความสัมพันธ์ (mix mapping) เข้า `RowLinks` ตอนย้ายข้อมูล ไม่งั้น traceback ของของเก่าขาดช่วง → ต้องดูโครงสร้างตารางผสมใน DB เดิมก่อนกำหนดวิธีแปลง

## คำถามที่ต้องตัดสินใจ
1. ผสมมีการ **สูญเสียน้ำหนัก** (ผลลัพธ์ < ผลรวมต้นทาง) หรือไม่ ต้องบันทึกส่วนต่างเป็นอะไร
2. ล็อตหนึ่ง **แบ่ง** ไปหลายรถเข็น/หลายล็อตผสมได้ใช่ไหม (ใช่ → ต้องตัดยอดแบบบางส่วน ซึ่งโมเดลข้างต้นรองรับ)
3. รถเข็นที่ผสมแล้ว ล็อตใหม่ใช้ **รหัสใหม่** (doc_number) หรือใช้ mapping_id เดิมต่อ
4. หน้า Traceback เดิมแสดงคอลัมน์/ขั้นตอนอะไรบ้างที่ห้ามขาด (ขอภาพหน้าจอหรือรายการคอลัมน์)
5. อุปกรณ์จริงที่มี: RFID 3 เครื่อง (TCP) ใช่ไหม มี scale/MQTT/เซนเซอร์อื่นหรือไม่ — ตัดสินว่า driver ไหนต้องทำก่อน
